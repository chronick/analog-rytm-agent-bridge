rytm-agent-bridge

A coding agent can play your drum machine — and undo everything it did.

The bridge exposes an Elektron Analog Rytm MKII to an agent as semantic operations: read a compact summary of the device, propose a change, and commit it on the next beat. Hardware has no ctrl-Z, so the whole design assumes the agent will sometimes be wrong — every persistent write is snapshotted as raw SysEx, verified by reading the device back, and restored byte-exactly when the readback disagrees.

$ npm run demo

In plain words: run the entire control plane — inspect, propose, validate, queue, apply, snapshot, roll back — against a mock device. No hardware, no MIDI cable, nothing at risk. It is the honest way to see what this does before it touches an instrument.

Run it without hardware first

Everything below runs against a mock Rytm transport. It needs no drum machine, no MIDI interface, and cannot touch a device.

1 Clone and install

The TypeScript side has zero runtime dependencies — npm install provisions only the dev-time type checker. Cargo resolves the Rust daemon.

$ git clone https://github.com/chronick/analog-rytm-agent-bridge
$ cd analog-rytm-agent-bridge && npm install

2 Drive the mock device

This walks the full lifecycle end to end and prints what each stage decided.

$ npm run demo

3 Run the whole gate

Node tests, the TypeScript typecheck, and the Rust daemon's cargo test in one command.

$ npm run check
before you plug anything in

Requirements are macOS (the daemon needs CoreMIDI and CoreAudio), Rust ≥ 1.89, and Node ≥ 22.14. When you are ready for the real device, work through HARDWARE_SETUP.md first — it covers MIDI port configuration, expected device settings, and the backup to take before any write test.

The safety model

This is the part worth reading. A drum machine is not a scratch directory — an agent that guesses wrong overwrites a kit you spent an evening building. Four rules follow from that, and they are enforced by the daemon rather than left to the agent's judgement.

→ Nothing mutates without --execute. Every hardware command runs validate-only by default: it connects, decodes real device state, checks the operation against it, and reports what would happen. The flag is the only way to write.

01

Validate against real state

Deltas are checked against the decoded contents of the connected device, not against an assumption about it. Unsupported operations fail as a refusal rather than a malformed object — an agent is expected to call rytm_describe_capabilities before anything else.

02

Snapshot the raw bytes

Before touching an object, the daemon stores the raw SysEx of each affected Pattern, Kit, Global, and Settings object durably — the original bytes, not a re-encoding of a decode.

03

Verify by reading back

After applying, the daemon re-reads the object from the device and compares it to what was asked for, canonicalizing codec-quantized values first so the comparison is real rather than cosmetic.

04

Roll back automatically

A failed readback restores the original raw bytes across every affected object, without ever decrementing the public revision. This path is hardware-certified against an injected failure, not just unit tested.

→ What it will still overwrite. The bridge protects the objects it knows it is touching. It does not back up your whole device. Save your projects to +Drive and take an external backup before first use.

→ Gestures stay non-persistent. Scene activation, performance macro amounts, and live parameter moves go out as transient CC/NRPN and never change the persistent revision — matching how the hardware itself treats them.

What one change actually does

Not "send MIDI and hope". A persistent edit moves through five stages, and the device gets the last word.

propose

The agent describes a delta — trigs, a machine, a kit parameter, a song row — against a compact state summary.

delta
validate

Checked against decoded device state and firmware capability. Dry run reports the exact effect.

+ snapshot
queue

Held for a musical boundary — next step, beat, measure, or pattern — resolved against an explicit transport epoch.

on the beat
apply → read back

Written, then re-read from the device and compared. Agreement commits the revision.

on disagreement → the original raw SysEx is restored across every affected object, the revision never moves backward, and the failure is journaled as an event the agent can read.

Boundaries come from real clock, not wall-clock guesses: the daemon either generates 24 PPQN or follows observed MIDI realtime input. It survives its own restart — queues, snapshots, revisions, and events are durable — and reconciles on reconnect, rejecting or rolling forward stale-epoch work.

The agent surface

Thirty-two semantic MCP tools. The vocabulary is deliberately about musical intent rather than SysEx addresses.

Undo, samples, and listening

rytm_snapshot_stateraw SysEx checkpoint
rytm_rollback_snapshotbyte-exact restore
rytm_upload_samplecontent-identified, no dupes
rytm_resolve_sample_ramslot assignment with readback
rytm_capture_pattern_audiobounded 48 kHz stereo take
rytm_capture_multitrack_audioOverbridge stems, optional

Capture is a first-class part of the loop, not an afterthought: the agent can play a pattern, record it, and analyze what came out. Takes are bounded, atomically finalized, and checked for silence, clipping, duration mismatch, dropped callback blocks, and disconnects — so a broken recording is reported rather than quietly analyzed.

A whole project from one declaration

Patterns, machines, sounds, scenes, performance macros, and samples described in JSON and applied validation-first, with snapshot and readback.

$ npm run build:project -- declaration.json --execute --auto-slots
{
  "project": "layered-kick-demo",
  "sounds": {
    "BD": {
      "machine": "bdplastic",
      "machineParams": { "tun": -14, "swt": 54, "dec": 45, "lev": 110 },
      "filter": { "filter_type": "Pk", "resonance": 40 },
      "amp": { "overdrive": 8 }
    }
  }
}

The sounds section designs each track's kit sound: a machine plus per-page parameter locks. The machine is emitted before its parameters, because selecting a machine resets its page to defaults — the kind of ordering detail that is invisible until it silently eats your settings.

A declaration with samples is preflighted against the device's RAM inventory before anything is applied. Each declared slot must be free or already hold that sample's own content; otherwise the run prints a conflict report and exits non-zero having changed nothing — instead of failing late, after every kit and pattern batch has already landed. --auto-slots remaps conflicts in memory, rewrites the p-locks and kit fields that referenced them, and stays idempotent across repeat runs. Slots the declaration does not own are never touched.

audition:project then plays each pattern from generated clock and captures a verified bounded recording per slot — so the output of a build is audio you can actually listen to.

Honest scope

What is certified, what merely works, and what is not there. "Certified" means run against a connected Analog Rytm MKII on OS 1.72, verified by readback, with the device restored to its exact pre-test state — the dated validation certificates in the repo are those runs.

AreaStatus
Patterns, kits, sounds, machinesCertified on OS 1.72 — inspect, delta, apply, snapshot, rollback
Scenes & performance macrosCertified — all 12 of each, declarative locks plus transient control
SongsCertified — rows, chains, repeats, per-position mutes, boundary scheduling
SamplesCertified — transfer, content identity, RAM resolution, kit rollback
Stereo audio captureCertified — bounded 48 kHz takes with fault detection
Overbridge multitrack captureCertified — Main, eight voice groups, external in, frame-aligned
Overbridge plug-in hosting / DAW automationnot implemented explicitly unsupported
Song tempo/length overrides, jumps, loops, labels, activationnot implemented

The codecs target firmware 1.70 and the certificates are from a 1.72 device. Neither is a blanket compatibility guarantee for other firmware — unknown-capability operations are gated rather than guessed at.

macOS only. The daemon depends on CoreMIDI and CoreAudio and does not build elsewhere.
